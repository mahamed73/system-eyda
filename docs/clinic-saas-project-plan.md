# مشروع: نظام إدارة العيادات (Clinic Management SaaS)
### وثيقة المشروع الشاملة — من الفكرة للتنفيذ

**الإصدار:** 1.0
**التاريخ:** أغسطس 2026
**نطاق الإطلاق الأولي:** أطباء وعيادات المنصورة

---

## 1. الفكرة في سطرين

نظام SaaS لإدارة العيادات بيربط بين 3 حاجات في مكان واحد: **حجز المواعيد**، **الملف الطبي للمريض**، و**الإدارة المالية والمخزون**. المستخدمين الأساسيين هما **الطبيب** و**السكرتارية/الاستقبال**، وهيبدأ التنفيذ محليًا مع عيادات في المنصورة قبل التوسع.

---

## 2. المشكلة اللي بيحلها المشروع

- أغلب العيادات الصغيرة والمتوسطة في المنصورة (ومصر عمومًا) لسه بتشتغل بدفاتر ورقية أو Excel متفرق.
- مفيش ربط بين **الحجز** و**الملف الطبي** و**الحسابات** — كل حاجة في مكان لوحدها أو مش موجودة أصلًا.
- السكرتارية بتضيع وقت في تنظيم المواعيد يدويًا، وبيحصل تعارض حجوزات (Double booking).
- الطبيب مش عنده رؤية سريعة على الإيرادات، المصروفات، أو المخزون (أدوية/مستلزمات لو العيادة بتبيع أو بتستخدم مستلزمات مباشرة).
- مفيش سجل تاريخي منظم لكل مريض (تشخيصات، وصفات، زيارات سابقة) يسهل الرجوع له.

---

## 3. الحل المقترح

منصة ويب (Web App) بتخدم كل عيادة كـ "مستأجر منفصل" (Multi-tenant) فيها:

1. **موديول المواعيد** — تقويم للعيادة، حجز/تعديل/إلغاء، تذكير للمريض (SMS/WhatsApp لاحقًا).
2. **موديول الملف الطبي** — بيانات المريض، تاريخ الزيارات، التشخيصات، الوصفات، المرفقات (تحاليل/أشعة).
3. **موديول الإدارة المالية والمخزون** — تسجيل الكشوفات والمدفوعات، تقارير الإيرادات، إدارة مخزون بسيط (أدوية/مستلزمات لو موجودة)، مصروفات العيادة.

النظام هيتقدم بموديل **تركيب + صيانة** (تفصيل في قسم 8) — يعني مش هيبقى Self-signup مفتوح، هيبقى فيه عملية بيع وتركيب شخصية للعيادة الأولى قبل التفكير في فتحه كمنتج ذاتي الاشتراك.

---

## 4. المستخدمين والأدوار (User Roles)

| الدور | الصلاحيات الأساسية في الـ MVP |
|---|---|
| **الطبيب (Owner/Admin)** | رؤية كاملة: مواعيد، ملفات مرضى، تقارير مالية، إدارة المخزون، إدارة حسابات الموظفين |
| **السكرتارية/الاستقبال** | حجز/تعديل مواعيد، تسجيل بيانات مريض جديد، تسجيل دفعة كشف، لا يرى تقارير مالية تفصيلية (قابل للتخصيص) |
| *(مستقبلًا)* محاسب | دخول محدود على الموديول المالي فقط |
| *(مستقبلًا)* مريض | بوابة حجز ذاتي عبر رابط عام (self-booking) |

## 5. نطاق الـ MVP (المرحلة الأولى)

بناءً على القرار: **إدارة العيادة بالكامل من أول يوم** (مواعيد + ملفات مرضى + مالية + مخزون)، لكن بحد أدنى وظيفي واضح لكل جزء عشان الـ MVP يخرج بسرعة معقولة:

### 5.1 موديول المواعيد
- تقويم يومي/أسبوعي للعيادة
- إضافة/تعديل/إلغاء موعد
- حالة الموعد: محجوز / حضر / لم يحضر / ملغي
- منع تعارض المواعيد (Double booking) تلقائيًا
- بحث سريع عن مريض عند الحجز

### 5.2 موديول ملفات المرضى
- بيانات أساسية: اسم، سن، تليفون، عنوان، ملاحظات عامة (حساسية أدوية مثلًا)
- سجل الزيارات: تاريخ، تشخيص، الوصفة، ملاحظات الطبيب
- إرفاق ملفات (صور تحاليل/أشعة) — تخزين بسيط
- بحث بالاسم أو رقم التليفون

### 5.3 موديول المالية والمخزون
- تسجيل كل كشف: سعر الكشف، طريقة الدفع (كاش/فودافون كاش مثلًا)
- تقرير إيرادات يومي/أسبوعي/شهري
- تسجيل مصروفات العيادة (إيجار، فواتير، مستلزمات)
- مخزون بسيط: صنف، كمية، حد أدنى للتنبيه (لو العيادة بتستخدم مستلزمات/أدوية بتتوزع)

### 5.4 خارج نطاق الـ MVP (يتأجل لمراحل لاحقة)
- بوابة حجز ذاتي للمريض
- تذكيرات SMS/WhatsApp تلقائية
- تطبيق موبايل مستقل
- تكامل مع معامل تحاليل/صيدليات
- فوترة إلكترونية متوافقة مع منظومة الضرائب (لو هيتوسع تجاريًا بشكل رسمي)
- تقارير BI متقدمة / الذكاء الاصطناعي في التشخيص

## 6. الكيانات الأساسية في قاعدة البيانات (Data Model — نظرة أولية)

```
Clinic (العيادة)
 └─ id, name, address, phone, subscription_status, created_at

User (مستخدم النظام)
 └─ id, clinic_id, name, role [doctor|receptionist], phone, password_hash

Patient (المريض)
 └─ id, clinic_id, name, phone, age, gender, notes, created_at

Appointment (الموعد)
 └─ id, clinic_id, patient_id, doctor_id, datetime, status, notes

Visit (الزيارة/الكشف)
 └─ id, patient_id, appointment_id, date, diagnosis, prescription, price, payment_method

Attachment (مرفق طبي)
 └─ id, visit_id, file_url, type [xray|lab|other]

InventoryItem (صنف مخزون)
 └─ id, clinic_id, name, quantity, min_threshold, unit_price

Expense (مصروف)
 └─ id, clinic_id, description, amount, date, category

Payment (دفعة/تحصيل)
 └─ id, visit_id, amount, method, date
```

هيتفصل أكتر في مرحلة تصميم الـ Schema الفعلي قبل الكود.

## 7. الاقتراح التقني (Tech Stack) — مناسب للتنفيذ عبر Claude Code

| الطبقة | الاقتراح | السبب |
|---|---|---|
| Frontend | **Next.js (React) + Tailwind CSS** | سريع في البناء مع AI، دعم ممتاز لـ RTL والعربي، SEO لو احتجت صفحة تسويقية |
| Backend | **Next.js API Routes أو Node.js/Express منفصل** | تبسيط الـ stack، سهل التعامل معه مع Claude Code |
| قاعدة البيانات | **PostgreSQL (عبر Supabase أو Railway)** | Multi-tenancy سهل، دعم ممتاز، فيه Auth جاهز لو استخدمت Supabase |
| المصادقة (Auth) | **Supabase Auth أو NextAuth** | جاهز، يوفر وقت تطوير كبير |
| الاستضافة | **Vercel (Frontend) + Supabase/Railway (Backend & DB)** | تكلفة بداية منخفضة، مناسب لعدد عيادات قليل في البداية |
| تخزين الملفات | **Supabase Storage أو Cloudflare R2** | رخيص لتخزين صور التحاليل/الأشعة |
| اللغة والاتجاه | **عربي RTL بالكامل** كواجهة أساسية، مع دعم أرقام/تواريخ ميلادي وهجري لو احتاج لاحقًا | يناسب طبيعة العملاء |

> ملاحظة: الاختيار ده يخليك تقدر تبني MVP سريع، وبعدين لو العدد كبر ونظام الـ Multi-tenant احتاج تحكم أدق، تقدر تنقل لبنية أعقد (مثلاً schema منفصل لكل عيادة أو حتى قاعدة بيانات منفصلة للعملاء الكبار).

## 8. الموديل التجاري: سعر تركيب + اشتراك صيانة

### 8.1 الفكرة
مش SaaS مفتوح للاشتراك الذاتي من أول يوم — البيع هيكون **مباشر (Door-to-door / علاقات شخصية)** مع الأطباء في المنصورة، بالشكل ده:

| المرحلة | الوصف | مثال سعري تقديري (تقدر تعدله حسب دراستك للسوق) |
|---|---|---|
| **رسوم التركيب (Setup Fee)** | تشمل: إنشاء حساب العيادة، تدريب الطبيب والسكرتارية، ترحيل بيانات مبدئية (لو فيه)، دعم أول أسبوعين | دفعة مقدمة واحدة (مثلاً 1,500 - 3,000 جنيه حسب حجم العيادة) |
| **اشتراك الصيانة الشهري** | يشمل: استضافة، تحديثات، دعم فني، نسخ احتياطي | اشتراك شهري ثابت (مثلاً 200 - 500 جنيه/شهر حسب عدد المستخدمين) |

### 8.2 ليه الموديل ده منطقي في مرحلة البداية
- بيقلل مقاومة الأطباء للتجربة (مش اشتراك مجهول عبر الإنترنت، فيه إنسان بيركب ويدرب).
- بيدي تدفق نقدي مبدئي (رسوم التركيب) يساعد في تغطية تكلفة التخصيص لكل عيادة.
- الاشتراك الشهري بيبني إيراد متكرر (Recurring Revenue) بمجرد ما تكبر قاعدة العملاء.
- بيسهل جمع Feedback مباشر من كل عيادة عشان تحسّن المنتج قبل التوسع.

### 8.3 خطة تسعير مستقبلية (بعد إثبات الفكرة محليًا)
لو العدد كبر ونظام الـ Self-signup بقى ممكن، ينفع تتحول تدريجيًا لموديل SaaS كلاسيكي (اشتراك شهري بدون رسوم تركيب، أو رسوم تركيب رمزية + خطط متدرجة: أساسية/احترافية).

## 9. خطة الإطلاق المحلي في المنصورة (Go-to-Market)

### المرحلة 1 — بناء الـ MVP (تقديري: 4-8 أسابيع حسب الوقت المتاح)
- تصميم الـ Schema والواجهات الأساسية
- بناء الموديولات الثلاثة بالحد الأدنى الوظيفي
- اختبار داخلي (نفسك تلعب دور طبيب + سكرتيرة)

### المرحلة 2 — عيادة تجريبية واحدة (Pilot)
- اختيار عيادة قريبة منك (معرفة شخصية تسهل الموضوع) تجرب النظام مجانًا لمدة شهر
- جمع ملاحظات حقيقية من الاستخدام اليومي
- تعديل الـ bugs والمشاكل العملية

### المرحلة 3 — أول 5-10 عيادات مدفوعة
- تفعيل موديل التركيب + الاشتراك
- تدريب كل عيادة شخصيًا
- بناء Case Study/شهادات من العيادات الأولى تساعد في البيع للي بعدهم

### المرحلة 4 — التوسع
- التوسع لمناطق تانية في الدقهلية أو محافظات مجاورة
- التفكير في موديل Self-signup لو النظام استقر
- إضافة ميزات متقدمة (بوابة مريض، تذكيرات تلقائية، إلخ)

## 10. التحديات والمخاطر المتوقعة

| الخطر | طريقة التعامل معه |
|---|---|
| مقاومة الأطباء للتغيير من الورق لنظام رقمي | التركيز على البساطة الشديدة في الواجهة + تدريب حضوري |
| مشاكل الإنترنت في بعض العيادات | التأكد من أداء خفيف للنظام، والتفكير مستقبلًا في وضع offline محدود |
| حساسية البيانات الطبية (خصوصية المرضى) | تشفير البيانات، صلاحيات واضحة، Backup دوري |
| الاعتماد عليك وحدك في الدعم الفني بداية | توثيق كل حاجة من أول يوم (عشان تقدر توظف أو تفوض لاحقًا) |
| صعوبة تسعير مناسب لسوق ناشئ | ابدأ بسعر تجريبي مرن مع أول عيادات وعدّل بناءً على ردة الفعل |

## 11. مؤشرات النجاح (KPIs) في المرحلة الأولى

- عدد العيادات اللي وقّعت واشتغلت فعليًا (مش بس اتفاق مبدئي)
- نسبة استخدام يومي فعلي (هل السكرتارية بتستخدم النظام فعلاً بدل الدفتر؟)
- عدد الشكاوى/الأعطال شهريًا (مؤشر استقرار النظام)
- معدل تجديد اشتراك الصيانة شهر بعد شهر (Churn Rate)

## 12. خطوات التنفيذ العملية (Roadmap تقني قبل التصميم)

1. **تجهيز الـ Schema النهائي** لقاعدة البيانات بناءً على قسم 6
2. **تصميم الـ Wireframes** الأساسية (شاشة الدخول، التقويم، ملف المريض، الشاشة المالية)
3. **إعداد بيئة العمل**: Next.js + Supabase + Tailwind
4. **بناء موديول Auth والـ Multi-tenancy** الأساسي (عيادة = tenant)
5. **بناء موديول المواعيد** (الأهم للاستخدام اليومي)
6. **بناء موديول ملفات المرضى**
7. **بناء الموديول المالي والمخزون**
8. **اختبار داخلي شامل**
9. **تجهيز مادة تدريب مبسطة (فيديو قصير أو صفحة توضيحية) للعيادة التجريبية**
10. **إطلاق تجريبي مع عيادة واحدة**

## 13. ملاحظات لاستخدام Claude Code في التنفيذ

- ابدأ بملف `PROJECT_CONTEXT.md` أو استخدم الملف ده نفسه كمرجع دايم يرجعله Claude Code في كل جلسة.
- اطلب بناء الموديولات **واحد واحد** مش كله مرة واحدة، وابدأ بـ Auth + Multi-tenancy الأول لأنه الأساس اللي كل حاجة تانية هتبني عليه.
- خلي كل موديول يتبني مع Migration file واضح لقاعدة البيانات عشان تقدر تتابع التغييرات.
- اطلب من Claude Code كتابة اختبارات بسيطة (Basic tests) للموديولات الحساسة زي المواعيد (منع التعارض) والمالية (حسابات الإيرادات).
